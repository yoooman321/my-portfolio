技術重點

以下皆對照現行程式碼整理；資料庫與部署相關的取捨見後面兩個區塊。

01

間隔重複排程引擎

六階段間隔（1／2／4／7／15／30 天）集中在 const/review.ts，取值一律透過 daysForStage()，夾取邏輯寫在函式內部，呼叫端無法拿到超出範圍的索引。

早期常數散落在三個檔案時，曾因為把「階段數量」寫在該放「最大索引」的位置而產生 off-by-one，最高階單字會算出 Invalid Date。

02

測驗題目生成與邊界降級

干擾選項取自同組其他單字，排除與正解同字或同義者，並以 Map 依語意去重，避免出現兩個意思相同的選項。

可用選項不足時自動縮減該題選項數，而不是拋錯或讓抽選迴圈跑不完。

03

時間序列統計的資料處理

複習紀錄以半開區間 [gte, lt) 查詢，避免邊界重複計算。

圖表資料先建立完整的日期骨架再填入查詢結果（gap filling），否則沒有複習的日期會直接從結果中消失、讓長條圖的時間軸失真。連續天數由同一份日期桶推算。

04

四張圖表全部手刻 SVG

熟練度甜甜圈、近 14 天複習量長條圖、12 週打卡熱力圖與連續天數，皆以原生 SVG 實作，未引入圖表函式庫。

數字以自製的 useCountUp hook 做動畫，並在使用者開啟 prefers-reduced-motion 時自動停用。

05

三個非語法層級的 React 問題

換題時因缺少 key，React 以「位置＋型別」判定為同一個元件實例，上一題的輸入與答題狀態會殘留；事件處理器讀到過期閉包（stale closure）而拿到更新前的值。

另一個是選項不足時在 Server Component 內跑不完的 while 迴圈——在 Node.js 單執行緒下會阻塞整個服務，而非只是單一分頁卡住。

06

語意化斷點的響應式改版

自訂 --breakpoint-nav 取代通用的 lg:，讓側邊欄、底部導覽列與主內容區的留白永遠依同一個斷點切換，調整斷點只需改一處，不會出現兩組導覽同時顯示。

另以 Tailwind v4 的 @utility 擴充 safe-area 的 padding。

幾個做過的決定

每個決定都連同「為什麼」與「代價」寫進專案文件，包括後來被推翻的。

07/18 → 08/27

從「不留歷史」到「留下每一筆」

首頁一開始就刻意不做「正確率」——沒有存作答歷史，硬做只會是假數字。

最初決定只存「可排程的狀態」，不留每次複習的歷史，理由是保持 schema 精簡。

做統計頁時才發現打卡日曆與趨勢圖做不出來——最後複習時間每次都被覆蓋，昨天的紀錄永遠救不回來。 曾考慮改用一個計數欄位，但那是「帳戶餘額」，你沒辦法從餘額反推出每一天存了多少錢。

明細可以推導出總計，總計推導不回明細。資料粒度一旦丟掉就回不來。

07/23

兩條刻意不對稱的排程規則

只有到期時答對才會進階——否則使用者可以在一個下午重複刷同一個字十次，系統就會以為他熟練了。

答錯一律退階，不管有沒有到期——「忘記」是客觀事實，跟排程無關。

兩條規則的不對稱來自這個功能真正的目的：長期記憶，不是短期分數。

08/24

停擺三週之後，選擇重排而不是硬趕

8 月初因現實生活因素中斷了三週。重啟時沒有假裝進度還在，而是重新盤點剩餘工作，把原訂三週的內容壓縮成兩週衝刺。

壓縮的代價是要砍功能，所以把「這次不做什麼」明確寫進排程文件，而不是默默延後。

承認中斷、重新估算，比假裝一切照計畫更能準時上線。

08/30

刻意不做冪等鍵

複習時要同時更新排程與寫入歷史，用交易綁成原子操作，外層加上最多五次的指數退避重試。

重試可能造成重複寫入，標準解法是加一個唯一的 idempotency key。評估後決定不做： 重試發生在同一個 Server Action 內、機率極低，後果只是圖表某天多算一次。

但把「什麼情況下該做」寫進了文件：跨網路呼叫、後果不可逆、高併發。

09/03

移除一個已經畫好設計稿的功能

統計頁原本有時間篩選 Tab。但版面調整後，數字卡固定顯示本月、熟練度是當下快照、 長條圖是近 14 天、熱力圖是 12 週——每一塊都有自己天然的時間範圍，那組 Tab 已經沒有東西可以控制。

一個點了沒反應的控制項，比沒有那個控制項更糟——使用者會以為 App 壞了。

09/04

用數據回答「需不需要 partition」

擔心複習紀錄長大後查詢變慢，於是建了一張兩百萬筆的測試表實際量測，而不是憑感覺加索引或提早分區。

情況執行計畫查一個月
沒有索引SCAN（全表掃描）70 ms
有索引SEARCH USING COVERING INDEX< 1 ms

結論是索引綽綽有餘，partition 解決的通常是維運問題而不是查詢速度。 並順手修正一個誤解：高基數不會讓索引變差，反而讓它更有效。

部署踩到的坑

三個都只在正式環境出現，本機再怎麼測都不會遇到。

靜態預渲染讓資料凍結

部署前讀 production build 的路由表，發現首頁和統計頁被標成靜態——資料會凍結在建置那一刻。 根因是 Next.js 只認得 fetch()，看不懂 ORM，所以判定這兩頁沒有動態資料。 開發模式每次都重新渲染，永遠不會重現。

原生查詢引擎裝不進 serverless

Prisma 的查詢引擎是 Rust 編譯的原生二進位，每個平台一份。 本機是 macOS arm64、雲端是 Linux x64，建置成功但一開頁面就 500。

官方文件的兩個解法在這個組合下都沒生效。最後改用 driver adapter + client engine—— 純 TypeScript／WASM，根本沒有平台專屬的檔案要打包，從源頭消除問題。

時區：本機正確、上線後每天錯八小時

資料本身永遠正確（時間戳是絕對時刻），錯的是「換算成日曆」那一步。 UTC 伺服器上，台北凌晨 0 到 8 點的操作全部會被記到前一天——熱力圖點錯格、連續天數可能無故斷掉。

解法是在伺服器啟動時統一時區，讓伺服器與使用者用同一本日曆。

技術

選 Firebase 是因為即時同步是這個產品的核心需求。

Vue 3 Vite Pinia Vue Router Firebase Realtime DB Firebase Auth Firebase Hosting

為什麼用 Firebase

課堂問答的核心是即時性——學生一按下答案，老師畫面的統計就要跟著跳。 自己架 WebSocket 伺服器要處理連線管理、重連、擴展； Firebase 的即時資料庫直接提供訂閱機制，加上 Auth 和 Hosting 是同一套， 對單人開發的專案來說是把力氣花在功能而不是基礎設施上。

介面全部自己設計

沒有設計稿也沒有 UI 框架的現成版型，從資訊架構到每個按鈕的位置都自己決定。 出題頁採「左側題目清單 + 右側編輯區」的雙欄結構， 讓老師在多題之間切換時不會迷失位置；未填寫的題目在清單上直接標紅， 送出前就知道哪裡還沒完成。

使用情境也影響了設計：上課只有短短幾分鐘，任何一個多餘步驟都會讓流程卡住。 所以學生端不做註冊、不打網址，掃 QR Code 輸入暱稱就開始； 成績檢討則反過來，允許從「總覽 / 玩家 / 問題」三個角度切入，因為那是課後慢慢看的。

同一套資料，課堂上要最快，課後要最完整——介面該長什麼樣，是使用情境決定的。

技術重點

皆對照專案程式碼整理。

01

信件的變數插入編輯器

以 Quill 自訂 Embed Blot，把 {顧客姓名} 這類變數做成不可編輯的標籤；可用變數由後端依信件類型提供，不寫死在前端。

存檔時把 Quill 產生的 DOM（含零寬字元 U+FEFF）清理成後端格式，載入時再轉回可解析的結構；並處理插入後的游標、捲動位置與選單開關。

02

長時間任務的輪詢 hook

把匯入、匯出的非同步任務合併成泛型 usePolling：前 60 秒每 3 秒輪詢、之後每 10 秒，15 分鐘逾時。

以 session id 防止舊任務的回呼覆寫新任務，callback 放在 ref 避免 stale closure，unmount 時清除計時器，並處理 429 限流與任務衝突。

03

動態維修表單與跨分頁預覽

故障原因的類型與選項可自由增減，用 dnd-kit 拖曳排序；前端資料模型與後端格式之間雙向轉換，選「其他」時前台顯示自填欄位。

預覽在新分頁開啟，以 BroadcastChannel 握手：預覽頁送出 READY，編輯頁回傳尚未儲存的內容，再用與前台相同的元件渲染。

04

Google Docs → Vue 轉檔工具

讓企劃在 Google Docs 寫好的內容，輸入文件 ID 就能轉成可直接放進專案的 .vue 檔，連同圖片一起打包下載。

公司內部工具，原始碼與畫面不公開；以下說明問題、流程與轉換規則。

原本的做法

每一篇內容，都要工程師從頭手工處理一次。

複製內文，再一段一段補上標籤

企劃把內容寫在 Google Docs，工程師要把文字複製進 .vue 檔， 逐段判斷該用 <h2>、<p>、<strong> 還是 <ul>， 再去 Google Drive 下載圖片、放到對應位置並寫上 import。

內容本身已經有結構，只是被困在文件裡——這種重複工作適合交給程式。

工具流程

工程師只剩最後一步：把檔案放進專案。

  1. 輸入 Doc ID企劃依固定格式撰寫文件，工程師只需提供文件 ID。
  2. 讀取文件透過 Google Docs API 取得文件內容與每段文字的樣式。
  3. 轉換並下載圖片產生 .vue 檔；依 imageUrl 從 Google Drive 下載圖片，並自動加上 import。
  4. 打包 .zip.vue 檔與圖片一起打包。放到對應位置、在 index.js 引入即可上線。

轉換規則

文件格式與企劃事先約定，工具才能穩定判讀。

文件中的內容轉成
title、description寫入元件 <script> 的 data
內文標題依字體大小或文件內建的標題樣式，轉為 <h2> 等標題標籤
一般段落<p>
粗體文字<strong>
項目清單<ul> / <li>
imageUrl從 Google Drive 下載圖片、在元件中 import，並一起放進 .zip

讓它能運作的前提

工具之外，還需要跟企劃一起把流程定下來。

和企劃約定固定的文件格式

title、description、imageUrl 與內文各有固定位置，工具才能準確判斷每段內容該轉成什麼。

事先取得 Google Drive 權限

圖片放在企劃的 Google Drive，先請企劃授予權限，工具才能自動下載，不必再人工一張張存檔。
